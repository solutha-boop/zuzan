Fixed in `journal.py`: added `_sync_custom_account()`, which mirrors a `CompanyAccount` row into a real `Account` row (mapping COA `group` → `AccountType`) the first time it's needed, called from `expense_account()`'s existing not-found fallback path (so it can never override an existing default/system account code). Verified with 6 targeted scenarios in a sandboxed DB: new custom expense account routes correctly; idempotent on a second post (no duplicate `Account` rows); custom Cost-of-Sales account also resolves correctly; a soft-deleted custom account still falls back to 5900 as before; an unmatched code still falls back to 5900; and a custom account whose code collides with an existing default account code does **not** override the default. All 6 passed.

**New finding surfaced while performing item 7's test — fixed this same session (post-report addendum #2, 19 September 2026, at the user's explicit request since the platform is already live):** the frontend's presentational `DEFAULT_COA` list (`App_js_fixed.js`, ~90 "Detail" line items like `6210 - Rent - Office`, `6910 - Income Tax Expense`) used a completely different code-numbering scheme from `journal.py`'s actual posting `DEFAULT_ACCOUNTS` (`5100`-series for salaries, `5900` General Expenses, etc.) — they were evidently built independently. Picking most default "Account" dropdown options when categorising an expense therefore either (a) fell back to 5900 General Expenses (the code doesn't exist in the ledger at all — the majority case, ~85 of ~90 codes), or, worse, (b) silently posted to a real but **wrongly-named** account, for the 5 codes that coincided by chance (`5110`-`5150`: selecting "5110 - Purchases" posted to the ledger account actually named "Payroll Levies (UIF/SDL)", since both lists happened to use 5110-5150 for different things). Confirmed the collision is scoped to exactly those 5 codes — the expense-category dropdowns only ever offer the "Cost of Sales" and "Expenses" groups (`EXPENSE_COA_GROUPS`), and cross-checked every code in those two groups against `journal.py`'s `DEFAULT_ACCOUNTS`; no other collisions exist. This does **not** affect aggregate totals (revenue, total expenses, EBIT, net profit) since misrouted amounts still land within `AccountType.expense`, but it did corrupt the per-account breakdown used in the AFS's expense-line disclosures.

Fixed with two changes:
1. **`journal.py`'s `expense_account()`** — when a submitted "{code} - {name}" doesn't match an existing ledger `Account` or a custom `/coa` account, it now auto-creates a new expense-type `Account` row using that exact code and name the first time it's posted, instead of silently falling back to 5900. This closes the ~85-code "doesn't exist in the ledger at all" majority case for every existing and future built-in COA option, with no data migration needed (accounts are created lazily, per company, on first use).
2. **`App_js_fixed.js` / `zuzan-app/src/App.js`'s `DEFAULT_COA`** (kept byte-identical, re-verified via sha256 after editing both) — renumbered the 5 colliding Cost-of-Sales codes from `5110`-`5150` to the free `5010`-`5050` range. This is a frontend-only, forward-looking change: it only affects what new selections store going forward: it does not touch or reinterpret any `Expense.category` string already saved on an existing expense.

**Known, accepted limitation (forward-looking fix only):** neither change retroactively reclassifies expenses already posted under the old, wrong routing — any expense already categorised via the old `5110`-`5150` codes has a journal entry that still points at the wrong (but real) account, and any expense already routed to 5900 by the pre-fix fallback stays there. Rewriting historical journal entries automatically is a materially different, higher-risk operation (it changes figures that may already be reflected in a period close, VAT return, or filed AFS) and was deliberately not attempted here. If the user wants those historical entries corrected, that should be a separate, explicitly-requested reclassification exercise — likely scoped per affected company, with the user reviewing which historical entries to touch before anything is changed.

Verified with 7 targeted scenarios in a sandboxed DB, covering: the old colliding code still resolves to the pre-existing (wrong) account unchanged (documents the accepted limitation, doesn't crash or silently "fix" history); the new renumbered code resolves cleanly with no collision; a never-before-seen built-in code (6210 Rent) auto-vivifies correctly instead of falling back to 5900; a second post to the same new code reuses the same `Account` row (idempotent, no duplicates); an explicit custom `/coa` account still takes priority over the generic auto-vivify path; the legacy bare-category matching path (`CATEGORY_TO_CODE`) is unaffected; and a genuinely unrecognised bare string still falls back to 5900 as before. All 7 passed. Re-ran the full 16-scenario payroll/journal balance test and the item-7 custom-`/coa` test afterward to confirm no regressions — both still 100% green.
